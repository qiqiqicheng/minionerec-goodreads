# 是否适合用 Unsloth 做当前 SFT

结论：**适合用于 SFT 训练侧的性能优化，但不建议替换当前 val/eval 主流程；优先做成一个可切换的训练 backend，而不是把现有 Lightning + PEFT 流程全部改掉。**

## 当前 SFT 任务形态

当前 SFT 不是普通 open-ended instruction tuning，而是围绕 SID 的多任务 causal LM：

1. `seq_sid_to_sid`：输入历史 SID，预测 next item SID。
2. `sid_to_title`：输入 SID，预测 title。
3. `title_to_sid`：输入 title，预测 SID。
4. `title_history_to_sid`：输入历史 title，预测 next item SID。

实现上已经具备：

- 自定义 tokenizer：在 base tokenizer 上追加 RQVAE 生成的 SID token。
- 自定义 label masking：prompt 部分 label 置为 `-100`，只对 response 算 loss。
- 训练模式：`full_finetune`、`new_token_only`、`qlora`。
- 当前默认配置是 Qwen2.5-3B-Instruct、LoRA target modules、bf16、gradient checkpointing、单卡 Lightning Trainer。
- 训练期 validation 分两部分：
  - `SFTModule.validation_step` 只算 teacher-forcing loss。
  - `SFTRecommendationValidationCallback` 每个 epoch 末抽样 256 条 valid row，做 constrained SID beam search，记录 `val/rec_MRR@10` 等指标并用于 checkpoint/early stopping。
- 离线 eval 通过 `scripts/eval.py` 对 export 后的模型做 random/popularity/base/SFT 对比，生成 HR/NDCG/MRR；backend 支持 HF constrained search 和 vLLM。

## Unsloth 能帮上的地方

Unsloth 最适合当前项目里的 **LoRA/QLoRA SFT 训练**，原因是：

1. **模型规模与显存约束匹配**  
   当前默认 base 是 Qwen2.5-3B-Instruct，单卡 3090/4090 24GB。这个规模用标准 Transformers + PEFT 可以跑，但在 `max_length=1744`、batch size 4、包含长 title history prompt 时，显存和吞吐都会比较紧。Unsloth 的 fused kernels、gradient checkpointing 和 4bit 路线正好针对这个场景。

2. **当前训练已经接近 Unsloth 的目标范式**  
   现有默认 `sft_qlora.yaml` 本质是 PEFT LoRA，target modules 也是 Qwen 常见的 `q_proj/k_proj/v_proj/o_proj/up_proj/down_proj/gate_proj`。如果切到 Unsloth，核心收益主要来自 model load + LoRA patch + 训练 forward/backward，而不是任务定义变化。

3. **可以保留现有数据构造**  
   `TokenizedSFTDataset` 已经直接产出 `input_ids/attention_mask/labels/task_id`，不依赖 HuggingFace `Trainer` 或 TRL。理论上可以让 Unsloth 加载并 patch 模型后，继续交给 Lightning 训练；不用重写样本构造、prompt 格式和 label masking。

4. **能为后续 RL 前的 SFT checkpoint 提供更好的性价比**  
   当前 routine 里已经记录第一次 4 epoch 效果差，第二次跑到 epoch 6 效果才可能变好。SFT 如果需要更多 epoch 或调参，训练吞吐会直接影响迭代速度，Unsloth 的收益比较实际。

## 不适合让 Unsloth 接管的地方

1. **不适合替换当前训练期 recommendation validation**  
   当前 `SFTRecommendationValidationCallback` 依赖 `constrained_sid_beam_search`，每一步要基于 SIDTrie 限制 allowed token，然后算候选 token 的 logprob。这个逻辑不是普通 `.generate()`，而是项目的核心评估约束。Unsloth 对训练 forward/backward 的收益更大，对这种 Python 侧逐步 constrained beam search 的加速有限。

2. **不适合替换离线 `scripts/eval.py`**  
   离线 eval 已经有 HF backend 和 vLLM backend。真正需要高吞吐评估时，vLLM 更适合；Unsloth 不是服务化/批量推理引擎。尤其当前 vLLM backend 已经支持 adapter eval，方向上比把 eval 改成 Unsloth 更合理。

3. **不适合直接用 Unsloth SFTTrainer 全盘重写**  
   直接迁移到 Unsloth 官方常见的 TRL/SFTTrainer 风格会丢掉当前这些项目特性：
   - Hydra 配置体系。
   - Lightning callback/checkpoint/early stopping。
   - `task_id` 分任务 loss 日志。
   - epoch-end recommendation validation。
   - 当前 export/eval manifest 约定。

4. **`new_token_only` 模式不太适合 Unsloth**  
   这个模式只训练新增 SID token embedding rows，并用 gradient hook mask 旧 vocab 行。Unsloth 的强项不是这种 embedding-row-only 微调；如果还要保留该模式，继续使用现有实现更直接。

## 最大风险点

1. **新增 SID token + LoRA/4bit 的兼容性**  
   当前代码先 `resize_token_embeddings(len(tokenizer))`，再做 LoRA/QLoRA，并且 export adapter 时 `save_embedding_layers=True`。Unsloth 接入时必须保持这个顺序和语义：
   1. 加载 base model/tokenizer。
   2. 添加 SID tokens。
   3. resize embedding。
   4. patch LoRA。
   5. 确保新增 embedding 能被训练和保存。

   如果 Unsloth 的推荐路径默认不训练/不保存 resized embedding，会导致 SID token 学不到或 export 后不可复现。

2. **和 Lightning 的边界需要验证**  
   Unsloth 常见示例多是配合 TRL/HF Trainer；当前项目使用 Lightning。原则上 Unsloth 返回的 model 仍是 `torch.nn.Module`，可以放进 LightningModule，但要实测：
   - backward 是否正常。
   - gradient checkpointing 与 Lightning precision 是否冲突。
   - checkpoint state_dict key 是否还能被 `export_sft.py` 正确加载。
   - `model.save_pretrained(..., save_embedding_layers=True)` 是否仍符合现有 export/eval。

3. **Unsloth 4bit 可能改变当前 load/export 约定**  
   现有 `sft_qlora.yaml` 里 `load_in_4bit: False`，名字叫 qlora 但实际更像 bf16 LoRA。若切到 Unsloth 4bit，需要同步调整：
   - train config 的命名和 manifest。
   - export 时是否要用 4bit 方式重建模型。
   - vLLM eval 是否能直接加载该 adapter 与 resized tokenizer。

4. **训练期 rec validation 可能成为瓶颈**  
   即使训练 forward/backward 被 Unsloth 加速，每个 epoch 的 256-sample constrained beam search 仍然逐样本、逐 SID token 调用模型。如果训练变快后，validation 占比会上升。可以考虑先把 `recommendation_validation.num_samples` 降到 64/128 做快速调参，最终 run 再恢复 256 或更多。

## 推荐落地方式

建议不要大改，而是做一个最小可回退集成：

1. 新增 `train_mode: "unsloth_qlora"` 或新增独立 config `model/sft_unsloth_qlora.yaml`。
2. 在 `SFTModule` 里增加 `_build_unsloth_lora_model()`，只替换模型加载和 LoRA patch 逻辑，保留：
   - `TokenizedSFTDataset`。
   - `SFTBatchCollator`。
   - `_shared_step` 和分任务 loss 日志。
   - `SFTRecommendationValidationCallback`。
   - 现有 optimizer/scheduler/checkpoint/export/eval。
3. 首先不要启用 full Unsloth Trainer，也不要改 `scripts/eval.py`。
4. 接入后的验收顺序：
   - debug 小样本：`data.max_train_samples=64 data.max_valid_samples=64 callbacks.recommendation_validation.num_samples=8 trainer.max_epochs=1`。
   - 检查 `train/loss`、`val/loss`、`val/rec_MRR@10` 都能正常出现。
   - export 一个 checkpoint，确认 `manifest.json`、tokenizer、adapter、SID index 都能生成。
   - 用 `scripts/eval.py --backend hf --num-samples 16` 跑通。
   - 再考虑 vLLM backend。

## 当前是否值得做

值得，但优先级应该是：

1. **如果标准 bf16 LoRA 已经能在 24GB 上稳定跑完，并且训练时间可接受**：暂时不必急着接 Unsloth，先把 SFT/RL pipeline 和指标闭环跑稳。
2. **如果接下来需要多轮 SFT 调参、增加 epoch、提高 max_length 或 batch size**：值得接 Unsloth，收益会比较明显。
3. **如果目标只是加速 val/eval**：不建议用 Unsloth，应该优化 constrained beam search 的 batching 或继续完善 vLLM backend。

我的建议：**把 Unsloth 作为 SFT 训练 backend 做窄集成，保留现有 Lightning/Hydra/validation/export/eval；先验证它能否正确训练新增 SID embeddings 和 LoRA adapter，再决定是否把默认 `sft_qlora` 切过去。**

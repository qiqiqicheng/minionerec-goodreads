# SFT 后评估与 RLHF 阶段计划

更新日期：2026-05-14

背景：当前已经完成第一次 SFT 训练；训练配置参考 `src/minionerec_goodreads/configs/train_sft.yaml`，只拿到了一个 epoch 级 checkpoint。这里不看 wandb log，只基于当前代码、配置、论文和已落盘的数据统计做下一步判断。

## 0. 先给结论

1. 这次 SFT 可以先当作有效 warm start，不建议因为“只有第四个 epoch ckpt”立刻重训。
   - 如果 checkpoint 文件名是 `epoch_004`，而 `trainer.max_epochs=5`，Lightning 的 epoch 通常从 0 计数，`epoch_004` 很可能就是第 5 个 epoch / 最后一轮。
   - 即使真的是第 4 个 epoch，只要 wandb 上各项 loss 都稳定下降、没有 non-finite loss、没有 recommendation loss 回升，也足够进入 eval/export 阶段。
2. 当前 24GB 本地机器可以做 `eval_sft` 和 `export_sft`。
   - Qwen2.5-3B bf16 推理权重大约 6GB 级别；constrained beam search 主要慢在多次 forward，不是显存爆炸。
   - `export_sft` 主要吃 CPU 内存和磁盘，GPU 不是瓶颈。
   - 先用 `max_samples=128` 做 smoke eval，再跑完整 test/valid。
3. RLHF 还没有实现，下一阶段不是直接开训，而是先把 SFT 结果定量化，再补一个最小 GRPO/RLVR 训练链路。
4. 资源上推荐：本地 24GB 负责 eval/export、RL 小样本 smoke、1.5B/3B QLoRA 调试；如果要跑 3B 正式 RL，优先再租 48GB，除非接受很慢的小 batch + gradient accumulation。
5. 面试叙事上，最值得讲的不是“我跑了 RLHF”，而是：SID 约束动作空间、beam 作为 group sampler、rank-aware reward 解决 sparse binary reward、以及为什么不用 collaborative reward 直接替代真实推荐目标。

## 2. 对本次 SFT 的初步评价

当前配置要点：

- backbone: `Qwen2.5-3B-Instruct`
- train mode: `model=sft_qlora`，当前文件内容是 `train_mode: qlora`
- LoRA target: q/k/v/o/up/down/gate projection
- `load_in_4bit: False`，所以严格说是 bf16 LoRA，不是 4-bit QLoRA
- `gradient_checkpointing: True`
- `trainer.max_epochs: 5`
- `data.batch_size: 4`
- `data.max_length: 512`
- checkpoint monitor: `val/loss_recommendation`

正面判断：

- 如果 wandb 上 `train/loss`、`val/loss`、`val/loss_recommendation` 都稳定下降，说明至少 prompt、label mask、SID token、LoRA 更新链路大概率是通的。
- 当前 callback 监控的是 recommendation loss，而不是纯混合 loss，这比只看 `val/loss` 更适合选择 checkpoint。
- 训练使用 48GB vGPU 是合理的，因为 3B LoRA bf16 + activation + optimizer 在 24GB 上可能能跑但余量很小，租 48GB 能减少无意义 OOM 调参。

保留判断：

- 没有 HR/NDCG 前，不能说 SFT 已经“推荐效果好”；只能说 SFT loss 正常。
- `load_in_4bit=False` 会让训练显存比真正 QLoRA 高，后续若在 24GB 上继续训练/RL，要么打开 4-bit，要么降到 1.5B。
- SFT 的任务混合包含 `seq_sid_to_sid`、`sid_to_title`、`title_to_sid`、`title_history_to_sid`，loss 下降可能部分来自 SID-title mapping；必须用 generation-time eval 验证 next-item ranking。

## 3. 24GB 上是否可以做 eval_sft / export_sft

### 3.1 eval_sft：可以，建议分三步

`eval_sft.py` 的评估方式是：加载 checkpoint/base model -> 构造 SID trie -> constrained beam search -> 计算 HR/NDCG/MRR、invalid/duplicate rate。

显存判断：

- Qwen2.5-3B bf16 权重大约 6GB 级别。
- LoRA adapter 很小。
- beam search 当前实现逐 prefix forward，没有一次性展开大 batch beams，所以显存压力可控，但速度会偏慢。
- `num_beams=10` 足够对应 HR@10/NDCG@10；如果后续和论文 RL 对齐，再用 beam 16。

推荐执行顺序：

1. valid 小样本 smoke：`max_samples=128, num_beams=10`
2. test 小样本 smoke：`max_samples=128, num_beams=10`
3. 完整 valid/test：`max_samples=-1 或不限制, num_beams=10`

要看的指标：

- `HR@3/5/10`, `NDCG@3/5/10`, `MRR@10`
- `invalid_rate`：constrained decoding 下应接近 0
- `duplicate_rate`：应很低；如果高，说明 SID collision/fallback 或 trie 去重还要检查
- qualitative examples：看 target SID 是否在 top beams 附近，而不是只看平均数

### 3.2 export_sft：可以，建议先 export 再正式 eval

`export_sft.py` 会保存：

- adapter 或 full model
- augmented tokenizer
- `goodreads.index.json`
- `goodreads.item.json`
- resolved config / manifest

当前 SFT 是 LoRA 模式，所以推荐导出 adapter，不要 merge 成 full model。这样最省磁盘，也最容易复现实验。

注意：

- 导出时 `--train-mode`、`--torch-dtype`、LoRA 参数必须和训练一致。
- 如果训练时没有 4-bit，导出/加载也不要随便加 `--load-in-4bit`，除非明确只是为了推理量化加载。
- 如果只保留云端 `.ckpt`，后续很容易因为 tokenizer/SID index 不一致而复现失败；export 是 RL 前的必要步骤。

## 4. RLHF 前必须完成的最小检查

不要从 SFT checkpoint 直接进 RL。推荐先完成下面 5 个 gate。

### Gate 1：导出 artifact

产物至少包括：

- exported adapter
- tokenizer
- manifest
- SID index hash
- item payload hash
- resolved hydra config

目的：保证 RL、eval 和未来答辩复现实验时用的是同一套 SID/tokenizer。

### Gate 2：SFT ranking eval

至少跑：

- valid recommendation eval
- test recommendation eval
- `seq_sid_to_sid` prompt
- 可选：`title_history_to_sid` prompt

如果 SFT 的 HR@10 仍接近 random，先不要 RL；否则 RL 只是在一个几乎不会生成有效目标的策略上做昂贵探索。

### Gate 3：baseline

至少做三个便宜 baseline：

1. random valid SID
2. popularity top-K
3. base Qwen-SID / 未 SFT checkpoint 的 constrained generation

这样面试里可以回答：SFT/RL 的收益到底超过了什么，而不是只报一个孤立的 HR@K。

### Gate 4：切片评估

建议加这些切片：

- seen target item vs new target item
- seen user vs new user
- history length bucket
- description-sourced item vs review-sourced fallback item
- SID length 4 vs SID length 5 fallback item

原因：当前 split 是 global chronological，不是 per-user leave-one-out；valid/test 里会有 train target 没出现过的 user/item。切片比单个总指标更能讲清楚模型边界。

### Gate 5：SID 健康口径

当前 SID 状态：

- items: 6,125
- raw unique code paths: 5,868
- raw collision rate: 4.1959%
- collided items: 257
- final SID length: 5,868 个 4-token SID，257 个 5-token fallback SID
- unique SID tokens: 757

这不阻塞 SFT/RL，因为最终 SID 是 item-level 唯一的；但它必须写进实验口径。面试里可以主动说：fallback token 解决了可寻址性，不等于 RQ-VAE 语义码完全无碰撞。

## 5. RLHF / GRPO 的推荐实现范围

这里更准确地说应该是 recommendation-oriented RLVR / GRPO，而不是传统 RLHF：没有人工偏好标注，也不训练 reward model；reward 来自 logged next item 和 ranking shaping。

### 5.1 最小可行版本

先只做 recommendation-only RL：

- prompt: `seq_sid_to_sid`
- train rows: 19,444
- candidates per prompt: beam width `G=8` 起步，稳定后再到 16
- policy: SFT LoRA adapter
- reference: frozen SFT adapter/base，用于 KL
- reward: `R = R_rule + λ * R_rank`
- optimizer: LoRA parameters only
- epoch: 先 0.1-0.2 epoch smoke，再 1 epoch，最后视结果决定第 2 epoch

不要第一版就把 SID-title alignment tasks 混进 RL。论文说 alignment 贯穿 SFT/RL，但个人资源下可以取舍：先保证推荐 RL 主链路正确，再考虑把 alignment batch 作为辅助 supervised loss 混进去。

### 5.2 采样策略

论文比较了 common sampling、dynamic sampling、beam search，最终用 constrained beam search width 16。

当前项目建议：

1. 第一版用 constrained beam search，不做 stochastic sampling。
2. 24GB 上先用 `G=8`，因为实现和调参更便宜。
3. 如果 valid HR@10 有提升，再用 `G=16` 对齐论文。

为什么 beam search 适合讲：

- SID 动作空间是闭集，重复采样很浪费。
- beam 天然给出不同 rank 的 hard negatives。
- 每个候选都是合法 item，reward 不被非法字符串污染。

### 5.3 Reward 设计

第一版 reward：

- rule reward：预测 item 等于 target，给 1，否则 0。
- rank reward：对非 target 候选按当前 beam rank 给负奖励，rank 越靠前惩罚越强。
- group normalization：在同一 prompt 的 G 个候选内标准化 advantage。

这样即使 target 没出现在 beam 里，也能通过 rank-aware negative shaping 给信号；否则纯 binary reward 会经常全 0，GRPO 更新很弱。

暂时不要做 collaborative reward：

- 原文 ablation 里 collaborative reward 反而退化，并解释为 reward hacking / reward 与真实目标不一致。
- 当前项目还没有 SASRec/GRU4Rec 这类可靠 teacher；为了省资源，不建议先训练一个 teacher 只为了 reward。
- 面试里可以把这个作为“我知道 reward 不能随便 densify”的例子。

## 6. 计算资源规划

### 6.1 本地 24GB 可以做的事

可以做：

- `export_sft`
- `eval_sft` smoke/full eval
- popularity/random/base model baseline
- RL 数据构造、reward 单元测试
- 1.5B 或 3B 的小样本 RL smoke
- 3B LoRA/QLoRA 极小 batch RL 调试

不建议做：

- 3B full finetune
- 7B SFT/RL
- beam 16 + 大 batch 的正式 GRPO
- 同时常驻 policy + reference + optimizer 且不用量化/LoRA 的训练

### 6.2 如果继续租 48GB

48GB 适合做：

- 3B LoRA/QLoRA 正式 GRPO
- beam width 16
- batch size 1-2 per device + gradient accumulation 到 effective batch 16-64
- 1-2 epoch RL

预计耗时取决于 rollout 实现。如果 rollout 是逐 prefix forward，速度会明显慢于普通 SFT；建议先在 1,000 prompts 上估算每 step 时间，再决定是否跑全量。

### 6.3 节省资源的路线

推荐路线：

1. 本地 24GB：export + eval + baseline。
2. 本地 24GB：RL smoke，`max_train_samples=256/1024`，`G=4/8`。
3. 如果 smoke 的 reward、KL、HR@10 都正常，再租 48GB 跑 3B RL。
4. 如果 48GB 成本仍然高，退而求其次：1.5B 跑完整 RL，用 3B SFT 作为主结果，1.5B RL 作为机制验证。

## 7. 推荐下一步执行顺序

### P0：今天就该做

1. 把云端 SFT checkpoint 拉到本地并固定路径。
2. 用 `export_sft.py` 导出 adapter/tokenizer/SID manifest。
3. 用 exported artifact 跑 valid/test smoke eval：`max_samples=128, num_beams=10`。
4. 跑完整 valid/test eval。
5. 保存 metrics JSON 和 20-50 条 prediction examples。

### P1：RL 前必须补

1. popularity/random/base-model baseline。
2. eval 切片：seen/new item、seen/new user、history length、SID length 4/5。
3. RL 数据类：只读取 recommendation rows，不混 item alignment。
4. reward 函数单测：target in beams、target not in beams、duplicate beams、all-negative beams。
5. policy/reference logprob 计算单测：确认只对 response SID tokens 算 logprob，不把 prompt 算进 loss。

### P2：正式 RL

1. 256 prompts smoke，G=4。
2. 1,024 prompts smoke，G=8。
3. valid eval 对比 SFT checkpoint。
4. 全量 train 1 epoch，G=8。
5. 如果提升明确，再 G=16 或第 2 epoch。

## 8. 面试中更值得挖掘的点

### 8.1 为什么 SFT loss 不等于推荐效果

SFT 是 token-level next-token loss，推荐评估是 item-level top-K ranking。SID 生成只要一个 token 错，item 就错；而且 mixed alignment loss 下降不代表 next-item ranking 变好。所以我会用 constrained generation 下的 HR/NDCG 来决定是否进入 RL。

### 8.2 为什么 RL 在这里不需要人工 reward model

推荐任务天然有 logged next item，可以构造成 verifiable reward。这里的 RL 更接近 RLVR：用规则 reward 和 ranking-shaped reward 优化生成策略，而不是收集人工偏好训练 reward model。

### 8.3 为什么 constrained decoding 是核心

如果不约束，LLM 会生成非法 SID、半截 SID 或不存在的 code path，reward 大量为 0，RL 会在无效动作空间里浪费算力。SID trie 把动作空间从自然语言 vocabulary 收缩到合法 catalog path，这正是生成式推荐和普通文本 RLHF 的差异。

### 8.4 为什么 beam search 比普通采样更合理

推荐 catalog 是闭集，重复采样很常见。beam search 能稳定给出一组 distinct hard negatives，并且 rank 本身可以进入 reward shaping。这比 naive top-k sampling 更省 rollout 成本。

### 8.5 为什么不直接用 collaborative model reward

看似 SASRec/GRU4Rec logit 能提供 dense reward，但 reward 不等于目标指标时会 reward hacking。原文 ablation 也发现 collaborative reward 退化。当前项目应先复现 rule + rank reward，把 teacher reward 作为后续扩展，而不是第一优先级。

### 8.6 如何诚实描述当前实验边界

需要主动说明：

- 当前 GoodReads split 是 global chronological，不是 per-user leave-one-out。
- item vocabulary / SID 是 transductive，全 catalog metadata 已用于 RQ-VAE。
- raw RQ-VAE path 有 4.2% collision，最终用 fallback token 保证 item 唯一。
- 当前是 6k item 的小 catalog，不能把绝对指标外推到工业亿级 catalog；但方法论上的 SID tokenization、constrained decoding、RLVR reward 是可迁移的。

## 9. 一句话计划

先不要急着重训 SFT；用现有 checkpoint 完成 export 和 constrained HR/NDCG eval。如果 SFT 已明显优于 random/popularity/base Qwen，再实现 recommendation-only GRPO：本地 24GB 做 smoke，48GB 跑 3B LoRA 正式 RL；reward 从 rule + rank 开始，不引入 collaborative teacher，最终用 SFT vs RL 的 HR/NDCG、diversity、切片指标讲清楚 RLHF 的真实收益。
